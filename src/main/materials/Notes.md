## Введение

- Spring многомодульный фреймворк
- Ядро Spring - SpringCore (содержит контекст для управления бинами)
- Бин - это объект java помеченный на включение в контекст приложения

## Способы добавления в контекст бинов:

### 1) Аннотация @Bean

    - создать класс конфигурации и пометить его как @Configuration

- Внутри класса добавить все нужные объекты и пометить каждый как @Bean
    - в Main функции при создании экземпляра контекста указать файл конфига

      ```java
      var context = new AnnotationConfigApplicationContext(AppConfig.class); 
      ```

- Если нужно несколько бинов 1 класса - присвой ему имя `@Bean(name = "kewa")`
- Если нужно пометить вариант бина по-умолчанию - пометь его как `@Primary`
- Аннотация @Bean удобна, когда нужен бин для класса, который не можете изменить, чтобы добавить в него
  стереотипную аннотацию

### 2) Стереотипные аннотации

- Сокращает код
- Отметить аннотацией @Component те классы, экземпляры которых вы хотите поместить в контекст Spring
- в классе конфигурации добавить путь, где искать компоненты приложения для
  контекста : `@ComponentScan(basePackages = "имя_пакета")`
- Стереотипные аннотации хороши всегда (меньше кода), а @Bean — лишь когда нет других вариантов
- Контролировать создание экземпляра можно через @PostConstructor с методом init (jakarta.annotation-api)
- Сделать что-то перед закрытием и очисткой контекста @PreDestroy (но нежелательно)
- `@Component` — базовый стереотип. Универсальная аннотация для любого Spring-компонента
- `@Service` — для сервисного слоя. Используется для классов, содержащих бизнес-логику
- `@Repository` — для DAO/репозиториев. Для классов, работающих с базой данных. (авто трансляция исключений БД в Spring
  исключения).
- `@Controller` — для веб-контроллеров. Используется в MVC для обработки HTTP-запросов (возвращает представления).
- `@RestController` — для REST API Комбинация @Controller + @ResponseBody. Используется для RESTful веб-сервисов.

- Задать дополнительные инструкции после создания бина: `@PostConstruct`
- Для этого нужно определить метод в классе компонента и снабдить этот метод аннотацией @PostConstruct
- Необходима зависимость `implementation("jakarta.annotation:jakarta.annotation-api:3.0.0")`

### 3) Программное добавление бинов (Spring 5)

- Добавление в контекст новых бинов используя существующие в контексте

```java
if(condition){

registerBean(b1); //Если условие истинно, добавить в контекст Spring некий бин
}else{

registerBean(b2); //Иначе: добавить в контекст Spring другой бин
}
```

- `Supplier` — это функциональный интерфейс, который входит в пакет Java.util.function.
- Назначение реализации Supplier - возвращать заданное значение, не принимая параметров.
- Чтобы программно добавить бин в контекст Spring, достаточно вызвать метод registerBean()

```java
<T> void registerBean(
        String beanName, // Имя бина, можно указать null если оно не нужно
        Class<T> beanClass, // Класс из которого создаем бин
        Supplier<T> supplier, // чтобы возвращать значение экземпляра, добавляемого в контекст
        BeanDefinitionCustomizer... customizers); // интерфейс, для настройки различных свойств бина
```

- Шаги:

1) Создание экземпляра, который будет добавлен в контекст Spring
2) Определение Supplier, который будет возвращать этот экземпляр
3) Вызов метода registerBean(), добавляющего экземпляр в контекст Spring

### Установка связей между бинами

- Способы:

1) Непосредственно вызывая методы создающие бины (монтаж - wiring)
2) Настройка Spring чтобы он предоставлял значение через параметр метода (авто монтаж — auto-wiring)
3) Внедрением зависимостей (dependency injection, DI)

#### Монтаж бинов путем прямого вызова одного метода с аннотацией @Bean из другого такого же метода

- Заключается в вызове одного метода из другого в классе конфигурации

#### Монтаж бинов путем передачи параметра в метод с аннотацией @Bean

- Внедрение зависимостей бина путем передачи параметра в метод (dependency injection, DI)

```java

@Bean
public Person person(Parrot parrot) { // Spring внедряет бин parrot в этот параметр
    Person p = new Person();
    p.setName("Ella");
    p.setParrot(parrot);
    return p;
}
```

### ВНЕДРЕНИЕ БИНОВ С ПОМОЩЬЮ АННОТАЦИИ @AUTOWIRED

- @Autowired - пометить свойство объекта, в которое мы хотим включить значение из контекста Spring
- Помечается в классе, куда нужно внедрить зависимость
- Три способа применения аннотации @Autowired:

1) внедрение значения в поле класса
2) внедрение значения через параметры конструктора класса
3) внедрение значения через сеттер

#### @Autowired в поле класса

- Класс помечаем как стереотипный - `@Component`
- В классе над нужным полем отмечаем - `@Aurowired`
- Применяя аннотацию @Autowired к полю класса, мы даем Spring команду
  присвоить этому полю значение бина, полученного из контекста. Spring создает
  два бина, person и parrot, и внедряет объект parrot в поле бина типа Person

- Недостатки внедрения зависимостей в поле класса:
- нет возможности отметить это поле как final
- при инициализации приходится самостоятельно управлять значением, а это
  сложнее

#### @Autowired в конструкторе

- Позволяет объявлять поле как `final`
- Удобнее для тестов (не нужно надеяться что в поле будет внедрен класс)
- Просто над конструктором класса указываем @Autowired и теперь в конструктор можно передать бин
- Начиная со Spring 4.3, если класс состоит только из одного конструктора, аннотацию
  @Autowired можно пропустить

#### @Autowired через сеттер

- код сложнее читать
- нельзя пометить поле как final
- тестирование не становится проще

## ЦИКЛИЧЕСКИЕ ЗАВИСИМОСТИ

- Это ситуация когда Spring создает бин `А` - но для него нужен бин `Б`, который
  в свою очередь требует бин `А`
- Нужно обратиться к перечисленным в терминале ошибок классам и убрать циклическую зависимость

## ВЫБОР ИЗ НЕСКОЛЬКИХ БИНОВ В КОНТЕКСТЕ SPRING

- Предположим, в контексте Spring есть три бина типа Parrot
- Согласно конфигурации фреймворк должен включить значение типа Parrot в параметр
- Возможны следующие варианты:
    - Идентификатор параметра совпадает с именем одного из бинов, добавленных
      в контекст. Spring выберет бин с таким же именем, как и у параметра

    - Идентификатор параметра не совпадает ни с одним из имен бинов, имеющихся в контексте
      Тогда можно поступить так:
        - отметить один из бинов как первичный (@Primary)
        - или выбрать некий бин и отметить его аннотацией @Qualifier

- Автор рекомендует использовать @Qualifier
- Она подчеркивает стремление внедрить определенный бин

## 4. Контекст Spring - использование абстракций

### 4.1. ПРИМЕНЕНИЕ ИНТЕРФЕЙСОВ ДЛЯ ОПРЕДЕЛЕНИЯ КОНТРАКТОВ

- Интерфейс Java это абстрактная структура
- Применяется для объявления определенных обязанностей
- Эти обязанности даются объекту, реализующему интерфейс
- Разные объекты могут реализовывать интерфейс по разному

#### 4.1.1. Использование интерфейсов для разделения реализаций

- Допустим один класс ссылается на метод другого класса
- Если нужно поменять метод - придется редактировать оба класса
  (имена класса и методов основного класса и зависимого)
- Можно основному классу использовать интерфейс, а из интерфейса реализовать множество классов с различной реализацией
- Тогда при изменении необходимого метода - нет нужды в редактировании основного класса

#### Условие задачи

Создать приложение, с помощью которого:
команда работников управляет своими обязанностями.
Одна из функций продукта — возможность оставлять заметки к задачам.
Когда пользователи публикуют комментарий, он где-то сохраняется (например, в БД)
Приложение отправляет письмо по mail, указанному в конфигурации приложения.

#### 4.1.3. Реализация сценариев использования без применения фреймворка

- На практике объекты выполняющие условие задачи - это сервисы
- Нужен сервис реализующий сценарий "Напечатать комментарий" (CommentService)
- Объект сохранения комментария - все что работает с хранением это репозитории (CommentRepository)
- Объект отправки по mail - все что коммуницирует с чем-то за пределами приложения это прокси (CommentNotificationProxy)
- CommentRepository и CommentRepository сделаем интерфейсами так как могут поменяться хранилища и способ отправки
- Реализуем контракты интерфейсов в DBCommentRepository и EmailCommentNotificationProxy
- Создаем класс Service (CommentService). В нем инициализируем поля интерфейсов
- Описываем логику использования интерфейсов
- Далее в программе создаем экземпляр сервиса и передаем ему в конструктор нужные реализации интерфейсов
- это DBCommentRepository и EmailCommentNotificationProxy

## 4.2.1. Выбор объектов для добавления в контекст Spring

- Интерфейсы и абстрактные классы не имеет смысла добавлять в контекст Spring
- Так же чаще не имеет смысла добавление record-классов
- Если есть доступ к редактированию класса - воспользуемся способом Component
    - `CommentService` — имеет две зависимости, от `CommentRepository` и `CommentNotificationProxy`;
    - `DBCommentRepository` — реализует интерфейс `CommentRepository` и является зависимостью для `CommentService`;
    - `EmailCommentNotificationProxy` — реализует интерфейс `CommentNotificationProxy` и является зависимостью
      для `CommentService` ;
- Снабдим классы `EmailCommentNotificationProxy`, `DBCommentRepository` и `CommentService` аннотацией `Component`
- Так как в классе  `CommentService` только 1 конструктор- Spring умен и подставит соответствующие компоненты в класс
- Аннотация @Autowired не обязательна (в `CommentService` только 1 конструктор)
- Так же понадобится класс конфигурации - назовем его `ProjectConfiguration`
- `ProjectConfiguration` снабжены аннотациями:
    - `@Configuration `- отметка, что это клас конфигурации
    - `@ComponentScan(basePackages = {"proxies", "services", "repositories"})` - в каких пакетах искать бины
- Теперь мы можем сформировать контекст Spring, извлечь оттуда бин типа CommentService и вызвать метод publishComment(
  Comment comment)

---

- Так же можно использовать @Autowired в поля класса CommentService (удалив его конструктор)
- Или оставить конструктор, и использовать в ProjectConfiguration аннотации @Bean

### 4.2.2. Выбор одной из реализаций абстракции для автомонтажа

- Допустим внедряемый объект имеет несколько реализаций. Чтобы выбрать одну из них можно:
    - отметить аннотацией @Primary тот из бинов, который будет выбираться по умолчанию;
    - присвоить бину имя с помощью аннотации @Qualifier и затем при DI обращаться к бину по этому имени

## 4.3. ПОДРОБНЕЕ ОБ ОБЯЗАННОСТЯХ ОБЪЕКТОВ СО СТЕРЕОТИПНЫМИ АННОТАЦИЯМИ

- Для лучшей читаемости соответствующие компоненты исходя из его назначения можно пометить вместо @Component как :
- @Service - для сервисов
- @Repository - для репозиториев

## Контекст Spring: области видимости и жизненный цикл бинов

- Область видимости (scope) - в мире фреймворка это вариант создания и управление жизненным циклом бинов
- Существуют scope типа `одиночка` и `прототип` (для WEB есть еще `запрос`, `сессия` и `приложение`)

### 5.1. Бины с одиночной областью видимости.

- Одиночная область видимости бина — вариант, выбираемый Spring по умолчанию для управления бинами в контексте
- Бывают `немедленные` и `ленивые`

#### 5.1.1. Что такое одиночный бин

- Spring создает одиночные бины при загрузке контекста и присваивает им имена (иначе, ID бина)
- При обращении к такому конкретному бину мы всегда получаем один и тот же экземпляр.
- В контексте Spring «одиночный» означает уникальность имени, но не уникальность наличия в пределах приложения

---

- **Singleton (Одиночный шаблон проектирования)**
- Один экземпляр класса на всё приложение
- Реализуется через private constructor + static getInstance()
- Жёсткое ограничение: только один объект класса
- **Одиночная область видимости (singleton scope)**
- Это определение относится к Spring
- Означает, что может существовать только один экземпляр с уникальным именем
- Но могут находиться несколько экземпляров класса, если у этих экземпляров разные имена
-

---

- *Создание бинов с одиночной областью видимости с помощью аннотации @Bean*
- Допустим 2 класса сервиса используют 1 репозиторий
    - Если пометить каждую реализацию сервиса как @Bean - то в контексте создадутся 2 бина
    - Если репозиторий тоже одиночный @Bean - то при обращении к бину репозитория все сервисы будут ссылаться
      на 1 и тот же объект репозитория

- *Создание бинов с одиночной областью видимости со стереотипными аннотациями*
    - Есть 1 класс Репозитория @Repository
    - Есть 2 класса сервиса, реализующих сервис @Service, которые используют @Autowired бина репозитория
    - В обоих случаях реализаций сервисы ссылаются на 1 и тот же бин репозитория.

#### 5.1.2. Одиночные бины в реальных приложениях

- Когда несколько потоков пытаются получить доступ к одиночному бину, они обращаются к одному и тому же экземпляру
- Если эти потоки одновременно попытаются изменить его, возникнет состояние гонки.
- Одиночные бины не рассчитаны на то, чтобы быть конкурентными
- Синхронизация потоков для конкурентности экземпляра резко снижает производительность приложения
- Рассчитаны как правило для определения базовой структуры классов и делегирования обязанностей между собой
- Одним из преимуществ внедрения в конструктор является возможность сделать экземпляры неизменяемыми(пометив поля бина
  как final)

#### 5.1.3 Немедленное и «ленивое» создание одиночных бинов.

- Для включения пассивного создания бина - снабжаем бин аннотацией @Lazy
- В Ленивом случае компонент создается в момент обращения к бину
- С точки зрения производительности лучше использовать немедленное создание бина в контексте
- При ленивом варианте проблема в коде бина может быть обнаружена только уже в работающем приложении (позже)
- Преимущество: экономия памяти

### 5.2 Бины с прототипной областью видимости.

- Каждый раз, когда запрашивается ссылка на прототипный бин, создается новый экземпляр объекта
- Для этого бин @Bean помечается как @Scope(BeanDefinition.SCOPE_PROTOTYPE)
- Для стереотипных аннотаций @Scope аналогично ставится перед классом @Component (или его подтипы)
- Решает проблему конкурентности доступа к бину

---

- Например, у нас есть бин CommentProcessor который обрабатывает комментарий перед отправкой (валидация и правка)
- Данным сервисом могут воспользоваться параллельно множество пользователей через компонент CommentService
- Не следует внедрять CommentProcessor непосредственно в бин CommentService
- Бин CommentService является одиночным, а следовательно, Spring создает только один экземпляр этого класса
- Таким образом, при создании бина CommentService Spring сразу внедрит и все зависимости класса
- В итоге получим единственный экземпляр CommentProcessor
- Правильно: использовать Prototype-бин внутри Singleton-бина!
    1) Пометить компонент CommentProcessor как стереотипный @Scope(BeanDefinition.SCOPE_PROTOTYPE)
    2) Внедрить контекст Spring (ApplicationContext) непосредственно в бин CommentService, используя аннотацию
       @Autowired
    3) Внедрить поле `@Autowired private ApplicationContext context;`
    4) Теперь мы можем через контекекст внутри логики червиса создать прототипный бин CommentProcessor
    5) В методе sendComment() бина CommentService теперь мы получаем каждый раз новый экземпляр CommentProcessor
    6) Отлично - сервис один, какк SingleScope, а процессор разделен как Prototype

---

- Как правило, стараются по возможности не использовать прототипные бины и изменяемые экземпляры
- Spring не следит за "прототипами" после их создания.
- Обычно в Spring-приложениях архитектуру строят так, чтобы сервисы были Stateless (без состояния).
- Если сервис хранит состояние, его сложно масштабировать и тестировать
- На практике обычноиспользуются одиночные бины, так как в этом случае при обращении по имени каждый раз возвращается
  один и тот же экземпляр, на данный экземпляр могут ссылаться несколько потоков. Поэтому рекомендуется делать такие
  экземпляры неизменяемыми. Но если вы решите выполнять операции, изменяющие атрибуты бина, необходимо обеспечить
  синхронизацию потоков
- Если нужно сделать бином изменяемый объект, лучше использовать прототипную область видимости

public class DatabaseConnection {

    }

            instance = new DatabaseConnection();

    }
