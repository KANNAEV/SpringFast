# Введение в Spring Boot и Spring MVC

- База, на которой строятся веб-приложения

## 7.1. ЧТО ТАКОЕ ВЕБ-ПРИЛОЖЕНИЕ

- Сейчас практически все нужные нам приложения — это веб-приложения.
- Разработчику крайне важно уметь их создавать

### 7.1.1. Основные сведения о веб-приложениях

- Любое веб-приложение состоит из двух частей:
    - Клиентская часть (frontend) - Представлена веб-браузером
    - Серверная часть —(backend) - получает запросы от клиента и отправляет ему в ответ данные
- Клиентов может быть много, и неправильный код серверной части может создавать состояния гонки на запросы клиентов

### 7.1.2. Способы реализации веб-приложений на основе Spring

- Веб-приложения по способу функционирования бывают разные
    - Backend в ответ на запрос клиента дает полностью готовое представление (В качестве ответа Backend предоставляет
      содержимое в виде HTML, CSS, а также в других форматах, которые браузер способен интерпретировать и вывести на
      экран). Применяется в основном для разделения уровня ответственности в сложных проектах.
    - Приложения с разделением обязанностей между Backend и Frontend (Backend отправляет только первичные данные (обычно
      представленные в JSON или XML). Браузер запускает клиентское приложение, которое получает первичный ответ от
      сервера, обрабатывает его и выводит данные). Применяется в основном для небольших приложений.

### 7.1.3. Использование контейнера сервлетов в веб-разработке

- Веб-браузер обменивается данными с сервером по сети через протокол HTTP
- HTTP аккуратно регламентирует данный процесс
- Контейнер сервлетов служит для Java-приложения переводчиком с HTTP
- Одним из самых популярных контейнеров сервлетов считается Tomcat
- Контейнер сервлетов умеет «говорить на языке HTTP». Он переводит HTTP-запрос для Spring-приложения, а ответ
  приложения — в HTTP-ответ. Благодаря этому можно не беспокоиться, какой протокол используется для передачи данных по
  сети, — достаточно представить все в виде объектов и методов Java
- Сервлет — это просто объект Java, который напрямую взаимодействует с контейнером сервлетов
- Если объект сервлета определен в Spring-приложении и зарегистрирован в контейнере сервлетов, и Spring, и контейнер
  знают о его существовании и могут им управлять

3) Укажите зависимости, которые нужно добавить в проект
4) Загрузите упакованный проект с помощью кнопки GENERATE
5) Распакуйте проект и откройте его в IDE


- Для следующего примера создадим такой проект с подключением компонента Spring Web

#### Класс main, созданный в start.spring.io
- снабжен аннотацией @SpringBootApplication
- Аннотация объявляет, что данный класс является главным классом приложения Spring Boot

#### Блок <parent> для Spring Boot Maven, созданный в start.spring.io
- добавлен родительский узел Spring Boot
- Он может выводить сообщение о совместимых версиях зависимостей, которые будут добавляться в проект.
- Таким образом Мы, как правило, не будем указывать версии зависимостей сами ( Spring Boot автоматически будет выбирать нужные, чтобы не возникло несовместимостей)

```XML pom.xml
<parent> 
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>2.3.4.RELEASE</version>
    <relativePath/>
</parent>
</parent>
```
#### Плагин Spring Boot Maven,настраиваемый start.spring.io
- Отвечает за дополнительные части стандартной конфигурации,

```XML pom.xml
<build>
    <plugins>
        <plugin>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-maven-plugin</artifactId>
        </plugin>
    </plugins>
</build>
```

#### Зависимости Maven, добавляемые start.spring.io при создании проекта
- `spring-boot-starter-web` - Это диспетчер зависимостей
- Во всех созданных нами примерах мы указывали версию каждой зависимости. Здесь это не понадобится, поскольку Spring Boot выбирает нужную версию автоматически. Именно для этого в pom.xml есть родительский узел Spring Boot:

```XML
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-web</artifactId>
</dependency>
```
#### Файл свойств приложения
- `application.properties`- в папке ресурсов служит для настройки параметров, необходимых в процессе выполнения приложения.

### 7.2.3. Автоматическая конфигурация по соглашению на основе зависимостей

- Когда мы добавили зависимость для веб-функционала, Spring понял, что нам понадобится контейнер сервлетов, и настроил экземпляр Tomcat 
— Как правило,разработчики используют контейнер сервлетов Tomcat
- SpringBoot Tomcat является контейнером сервлетов по соглашению
- Соглашение — это наиболее частый вариант конфигурации приложения для вы-полнения определенных задач


## 7.3. РЕАЛИЗАЦИЯ ПРИЛОЖЕНИЯ С ПОМОЩЬЮ SPRING MVC
- Чтобы добавить в веб-приложение новую страницу, нужно выполнить следующие операции
  - Создать HTML-документ в resources/static
  - Создать контроллер с соответствующим действием для этой HTML-страницы 

- Контроллер — это компонент веб-приложения, который содержит методы (действия), выполняемыми для определенных HTTP-запросов.
- Класс контроллера (MainController) пометим аннотацией`@Controller`
- Метод контроллера, возвращающий html документ пометим аннотацией 	`@RequestMapping("/home")`
```java
// Контроллер - возвращает ссылку на веб-страницу, которую приложение дает в ответ на запрос
@Controller
public class MainController {
	@RequestMapping("/home")
	public String home() {
		return "home.html";
	}
}

```
- После зупуска приложения нам доступен Веб-сервер  по адресу http:/localhost:8080/home
- По ссылке на /home получаем нашу HTML-страницу
- Последовательность работы приложения:
1) Клиент делает HTTP-запрос
2) Tomcat получает HTTP-запрос клиента и вызывает компонент сервлета, ответственный за его обработку. В случае Spring MVC это сервлет, указанный в конфигурации Spring Boot. Его мы называем сервлетом-диспетчером (dispatcher servlet)
3) Сервлет-диспетчер является точкой входа в веб-приложение Spring. Tomcat вызывает сервлет-диспетчер для всех полученных HTTP-запросов. Его обязанность — управлять запросами в Spring-приложении. Диспетчер должен найти действие контроллера, которое вызывается в ответ на данный запрос, и определить, что следует вернуть клиенту. Этот сервлет еще называют фронтальным контроллером или единой точкой входа (front controller)
4) Сервлет-диспетчер ищет действие контроллера для ответа на запрос. Чтобы определить, какой контроллер нужно вызвать, сервлет делегирует управление компоненту, который называется картой обработчиков (handler mapping). Она находит действие контроллера, связанное с запросом через аннотацию @RequestMapping
5) Когда нужное действие контроллера будет найдено, сервлет диспетчер вызывает его. Если на карте обработчиков не нашлось ни одного действия, связанного с запросом, приложение выдает клиенту HTTP-статус 404 — Not Found. Если же действие есть, контроллер возвращает сервлету-диспетчеру имя страницы,которую нужно отобразить. Ее принято называть представлением(view)
6) В этот момент сервлет-диспетчер должен найти представление, имя которого было предоставлено контроллером, получить содержимое представления и отправить его клиенту Сервлет-диспетчер делегирует обязанность получить содержимое компоненту, который называется арбитром представлений (view resolver)
7) Сервлет-диспетчер возвращает сгенерированное представление клиенту в виде HTTP-ответа

# Реализация веб-приложений с использованием Spring Boot и Spring MVC

## 8.1. СОЗДАНИЕ ВЕБ-ПРИЛОЖЕНИЙ С ДИНАМИЧЕСКИМИ ПРЕДСТАВЛЕНИЯМИ
 - Большинство современных приложений предоставляют пользователю динамические данные
 - Чтобы знать, что отображать, динамическое представление получает изме- няющиеся данные от контроллера
 - В Spring реализован простой способ создания динамических страниц для веб-приложений с помощью таких шаблонизаторов, как Thymeleaf Кроме Thymeleaf, есть и другие варианты, например Mustache, FreeMarker и Java Server Pages (JSP)
 - Создадим проект SpringBoot и добавим шаблонизатор в раздел зависимостей файла pom.xml
 - `Thymeleaf` — это зависимость, позволяющая легко передавать данные из контроллера в представление и выводить их определенным образом

- Добавим зависимость `spring-boot-starter-thymeleaf` в блок <dependency>
- Аналогично добавим `spring-boot-starter-web` так как это веб-приложени
- Thymeleaf использует объект Model (или ModelAndView) для передачи данных из контроллера в шаблон
- Для контроллера определим параметр метода Model, который контроллер будет передавать в представление
- В экземпляр Model мы добавим значения, которые также должны отправиться в представление
- Каждое из них будет иметь уникальное имя (еще называемое ключом)
- `addAttribute(ключ:значениее)` -  добавит новое значение,которое контроллер будет передавать в представление
- поскольку мы используем шаблонизатор и работаем над динамическим представлением, нам нужно разместить HTML- файл в папке resources/templates
- Thymeleaf заменяет содержимое тега на значение из атрибута th:text
- Он НЕ вставляет текст между открывающим и закрывающим тегом, а полностью заменяет всё содержимое
```HTML
<span th:text="${username}">Этот текст будет полностью заменен на `username` </span>
```

- ` Thymeleaf` для ускорения работы кеширует шаблоны (мешает для динамического редактирования)
-  В `application.properties` для группы `spring.thymeleaf` можно установить 
  - `cache: false` - отключает кеш
  - `prefix: file:src/main/resources/templates/ ` -  миновать classpath. Теперь Spring читает шаблоны НАПРЯМУЮ ИЗ ИСХОДНИКОВ

## 8.1.1. Получение данных из HTTP-запроса

- В большинстве случаев данные передаются посредством HTTP-запроса одним из следующих способов
  - в виде` параметра HTTP-запроса` — в формате пары «ключ—значение» Параметры добавляются в URI каквыражения запроса (хорош для передачи небольших объемов данных);
  - в виде `параметров заголовка HTTP-запроса`. Так же передаются в заголовке HTTP-запроса, но параметры заголовка не попадают в URI. Этот способ также не подходит для больших объемов данных;
  - `переменная пути` передает данные через сам путь запроса. Как и в случаях выше, переменные пути используются для небольших объемов данных. Но данный вариант передачи следует применять, если данные являются обязательными;
  - `в теле HTTP-запроса ` - когданужно передать много данных (строки, но иногда и двоичные данные, такие как файлы) 

### 8.1.2. Передача данных от клиента серверу посредством параметров запроса

- Параметры запроса применяют в следующих случаях:
  - Если объем данных не очень велик. Параметры запроса задаются посредством переменных запроса (Максимум около 2000 символов);
  - Если нужно передать необязательные данные. 
  - Параметры запроса — простой способ выслать значения, которые клиент не обязан передавать. Сервер будет готов не получить значения определенных параметров запроса.

  > Предположим, приложение выводит товары и их свойства в виде таблицы\
  `наименование`, `цена` и `бренд` \
   Мы хотим, чтобы пользователь мог найти товар по любому из этих критериев или по сочетанию данных характеристик \
   Здесь было бы правильно использовать параметры запроса \
   Приложение отправляет значения (наименование,цену,бренд) в виде необязательных параметров \
   Клиенту нужно передать только те из них, по которым пользователь решил выполнить поиск.


- Чтобы извлечь значение из параметра запроса, нужно добавить в метод действия контроллера еще один параметр и снабдить его аннотацией @RequestParam
- Она сообщает Spring, что нужно извлечь значение из параметра HTTP-запроса
- Имя параметра должен совпадать с параметром метода
- В адресной строке веб-браузера URI запроса имеет вид типа
- `http://localhost:8080/home?color=blue`
- Параметры следуют после адреса страницы и знака `?`
- Через анперсанд можно передать несколько параметров
- Их и ожидает @RequestParam
```java
@Controller
public class MainController {
	@RequestMapping("/home")
	public String home(@RequestParam String color, Model page) {
		page.addAttribute("username", "GeriLewy");
		page.addAttribute("color", color);
		return "home.html";
	}
}
```
- Теперь при запроск к странице Home метод контроллера получает параметр color = "blue"
- Но если не передать параметр теперь страница не возвращается
- Для этого нужно указать значение по-умолчанию: 
- `@RequestParam(value = "color", defaultValue = "blue") String color, Model page)` 

### 8.1.3. Передача данных от клиента серверу с помощью переменных пути
- в этом случае мы явно вставляем переменные в путь
- `http://localhost:8080/home/blue`
- с большим количеством переменных путь становится трудно читать
- Обычно их используют только для обязательных параметров
- Не могут использоваться для необязательных значений
- Переменные пути легче читать, чем переменные запроса.
- страницы с переменными пути легче индексируются поисковыми системами (такими как Google)
- Настройка контроллера для переменного пути:
  - добавить в путь имя этой переменной, заключенное в {фигурные скобки}
  - Аннотацией `@PathVariable` отметить параметр действия контроллера, в котором будет передаваться значение переменной пути
  - http://localhost:8080/home/red?user=Admin - по данному пути получим 2 параметра,один по переменной пути а второй посредством параметра запро
  ```java
  	public String home(
			@PathVariable String color,
			@RequestParam(value = "user", defaultValue = "User", required = false) String user,
			Model page) {
		page.addAttribute("user", user);
		page.addAttribute("color", color);
		return "home.html";
	}
  ```

## 8.2. ИСПОЛЬЗОВАНИЕ HTTP-МЕТОДОВ GET И POST
- До сих пор мы говорили только о пути и, сами того не сознавая, использовали HTTP-метод `GET`
- Назначение HTTP-метода — определить действие, которое запрашивает клиент
- Основные HTTP методы: 
  - GET     (получить данные)
  - POST    (передача данных для сохранения на сервере)
  - PUT     (изменить данные, хранящиеся на сервере)
  - PATCH   (частичное изменение данных, хранящихся на сервере)
  - DELETE  (удаление данных на сервере) 

- При реальной разработке между PATCH и PUT часто не делают различий
- Но хороший тон различать их для лучшего понимания цели запроса

 > Предположим, нам нужно создать приложение, которое сохраняет список товаров\
 У каждого продукта есть наименование и цена\
Веб-приложение выводит перечень всех товаров\
 Пользователь может добавить туда один или несколько продуктов посредством HTML-формы

- Просмотреть список товаров: метод GET
- Добавить товары в список: метод POST

1) Создадим модель продукта: класс Product 
2) Создадим сервис : ProductService
3) Реализуем в сервисе 2 сценария: получение списка товаров и добавление нового (пока не обращаем внимание на область видимости бинов и возможном состоянии гонки)
4) Контроллер ProductController - будет вызывать сценарии сервиса
5) В конструкторе контроллера для доступа к бину сервиса используем DI
6) В контроллере реализуем первый сценарий : вывод списка товаров (viewProducts)
  - @RequestMapping("/products"); По-умолчанию аннтоация использует GET
  - Можно заменить на @GetMapping("/products")
  - Принимает параметр типа Model для передачи данных в представление
  - Получаем от сервиса список товаров в переменной `products`
  - Передаем полученный список в model-представление
  - возвращаем имя представления диспетчеру сервлетов

7) В контроллере реализуем второй сценарий : добавление товара (addProducts)
 - Создадим метод addProduct с аннотацией: 
  - `@RequestMapping(path = "/products",
                method = RequestMethod.POST)`
  - Можно заменить на @PostMapping("/products")
  - Параметры метода:с @RequestParam отметим 2 параметра которые ожидаем получить и 1 параметр Map для сборки запроса и передачи в сервис


- В приложениях часто использую

Шаблонизатор — это зависимость, благодаря которой в приложении появ- ляется возможность легко получать данные, передаваемые контроллером, и выводить их в представлении

- Клиент может отправлять данные на сервер в виде параметров запроса или переменных пути. Действие контроллера получает эти данные в виде параметров аннотации `@RequestParam` или `@PathVariable` соответственно
- Параметры запроса не являются обязательными
- Переменные пути следует использовать только для обязательных данных, передаваемых клиентом
- HTTP-запрос характеризуется HTTP-методом и путем. HTTP-метод описывается ключевым словом,соответствующим намерениям клиента Напрактике,как правило, вам будут встречаться следующие HTTP-методы: GET, POST,PUT, PATCH и DELETE
- Для передачи данных непосредственно из HTML-формы в браузере можно применять только HTTP-методы GET и POST.
- Чтобы использовать остальные методы, такие как DELETE и PUT, нужно написать код вызова на клиентском языке программирования, таком как JavaScript
