# 10 REST
- REST (Representational State Transfer — передача состояния представления)
- REST ­сервисы — это способ обмена данными между двумя приложениями. 
- Обращаться к бэкенду с помощью конечных точек REST может не только клиент веб­приложения или мобильное приложение. 
- Сервисы бэкенда также могут обмениваться данными посредством REST ­вызовов

## 10.1. ОБМЕН ДАННЫМИ МЕЖДУ ПРИЛОЖЕНИЯМИ ПОСРЕДСТВОМ REST-СЕРВИСОВ
- Конечные точки REST — это всего лишь способ организовать коммуникацию между двумя приложениями
- Это обычное действие контроллера, связанное с HTTP-методом и путем
- Приложение вызывает действие контроллера через HTTP
- Конечные точки можно назвать веб-сервисами
- После завершения действия контроллера диспетчер сервлетов не формирует представление, а сразу передает HTTP ­ответ

## 10.2. СОЗДАНИЕ КОНЕЧНОЙ ТОЧКИ REST
- Применение аннотации @ResponseBody, которое приводит к дублированию кода
```java
@Controller
public class HelloController {
    @GetMapping("/hello")
    @ResponseBody
    public String hello() { return "Hello!";}
    @GetMapping("/ciao")
    @ResponseBody
    public String ciao() { return "Ciao!";}
}
```
-  Аннотация @RestController, позволяющая избавиться от дублирования кода
```java
@RestController.   // Вместо повторения аннотации @ResponseBody перед каждым методом, заменяем @Controller на @RestController
public class HelloController {
    @GetMapping("/hello")
    public String hello() {return "Hello!";}
    @GetMapping("/ciao")
    public String ciao() {return "Ciao!";}
}
```

- Инструменты, позволяюще обращаться к конечным точкам:
    - Postman — имеет приятный GUI
    - cURL — инструмент командной строки (curl -X GET http://localhost:8080/hello)

## 10.3. УПРАВЛЕНИЕ HTTP-ОТВЕТОМ
- HTTP-ответ — это тот способ, которым серверная часть приложения возвращает данные клиенту в ответ на его запрос
- В HTTP-ответе содержится следующая информация:
    - заголовок ответа (небольшие фрагменты данных, как правило не длиннее пары слов)
    - тело ответа (более крупный объем данных направлеемый клиенту в ответ)
    - статус ответа (краткое представление результата запроса)
### 10.3.1. Передача объектов в теле HTTP-ответа
- Если контроллер возвращает на GET запрос объект, SPRING оздает строку, представляющую объект, и дает ее в формате JSON
- JavaScript Object Notation (JSON) — это простой способ представления строк в виде пар «атрибут — значение»
- Можно использовать в Spring другие форматы для тела запроса (такие как XML или YAML), подключив к объектам специальный преобразователь

### 10.3.2. Создание HTTP-ответа со статусом и заголовками
- Иногда бывает удобнее передать часть данных в заголовке ответа
- Самый простой и наиболее распространенный способ изменить HTTP-ответ — применить класс `ResponseEntity`
- `ResponseEntity` позволяет модифицировать тело, статус и заголовки HTTP-ответа

### 10.3.3. Управление исключениями на уровне конечной точки
- Рассмотрим один из самых важных паттернов обработки ошибок в REST API
```
Клиент (POST /payment)
    ↓
PaymentController (принимает запрос)
    ↓
PaymentService (бизнес-логика)
    ↓ (если ошибка → throws NotEnoughMoneyException)
    ↓
Controller перехватывает ошибку → возвращает понятный ответ клиенту
```
- Для его реализации создается в контроллере используется try-catch
- catch отлавливает нужное исключение
- создается свой класс исключения, наследуемый от RuntimeExeption (необрабатываемые исключения)
- Если сервис возвращает исключение в блок try - то выполняется логика в блоке catch
---
- *Проблема:* 
    - Одно и то же исключение может возникнуть в 100 разных контроллерах. 
    - Писать в каждом try-catch — плохо (дублирование кода, сложность поддержки).
- *Решение:* 
    - В Spring Boot есть механизм советов (`Advice`) — это глобальная обёртка над контроллерами. 
    - Spring сам подставляет этот код во все контроллеры.
- *Как работает:*
    -   Контроллер просто выбрасывает исключение (без try-catch), а совет его перехватывает и формирует красивый HTTP-ответ.
- *Реализация:*
    - Создаём класс в пакете `controllers.advice` (например, `ExceptionControllerAdvice`).
    - Ставим аннотацию `@RestControllerAdvice` — она делает этот класс глобальным перехватчиком для всех REST-контроллеров.
    - Внутри создаём методы, которые возвращают `ResponseEntity`.
    - Каждый метод помечаем `@ExceptionHandler(ИмяИсключения.class)` — так мы привязываем метод к конкретному исключению.
    - Внутри метода собираем нужный статус, заголовки и тело ответа в `ResponseEntity` .

- *Дополнительно:*
    - На практике вам иногда придется передавать из действия контроллера в совет дополнительную информацию о возникшем исключении
    - В таком случае нужно добавить параметр к методу-обработчику исключения в классе совета
    - Spring догадается, что нужно передать из контроллера в метод-обработчик ссылку на исключение 
    - Затем можно будет использовать в логике совета любую информацию, извлеченную из экземпляра исключения

## 10.4. ИЗВЛЕЧЕНИЕ ДАННЫХ ИЗ ТЕЛА ЗАПРОСА, ПОЛУЧЕННОГО ОТ КЛИЕНТА

- Мы можем передавать данныев HTTP-запросе, используя параметры запроса и переменные пути
- Конечные точки REST создаются точно так же, как и действия контроллера для веб-страниц
- у HTTP-запроса есть тело и его можно использовать для передачи данных от клиента серверу
- Тело HTTP- запроса часто используется при отправке информации в конечные точки REST
- Если нужно передать большой объем данных следует использовать тело запроса
- Чтобы передать данные в теле запроса, достаточно снабдить параметр действия контроллера аннотацией `@RequestBody`
- Spring ожидает данные в формате JSON и пытается преобразовать строку JSON в объект, соответствующий типу параметра
- Если фреймворку это не удается,приложение возвращает HTTP-ответ со статусом 400 Bad Request




# 11 Использование конечных точек REST 
- В серверных решениях, состоящих из нескольких сервисов компонентам нужен способ «поговорить друг с другом» и обменяться данными
- Реализация конечной точки /payment в классе контроллера в простом виде можно просмотреть в `task6`
- Конечная точка ожидает запрос POST с параметром заголовка `requestId` и объектом `Payment`
- Далее мы будем использовать к данной конечной точке вызовы из другой программы (запущенной на другом порту)
- Рассмотрим 3 таких способа для вызова конечных точек из микросервиса payments `task6`

## 11.1 Вызов конечных точек REST с помощью OpenFeign из проекта Spring Cloud.
- Схема планируемого взаимодействия OpenFeign-клиента с микросервисом обработки платежей :
```
┌─────────────────────────────────────────────────────────────────┐
│                    Клиент (например, Postman)                   │
└──────────────────────────┬──────────────────────────────────────┘
                           │ POST /payment
                           │ {"amount": 150.50}
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│            PaymentsController (Ваш текущий сервис)              │
│  1. Получает запрос от клиента                                  │
│  2. Генерирует requestId                                        │
│  3. Вызывает PaymentsProxy (Feign)                              │
└──────────────────────────┬──────────────────────────────────────┘
                           │ Feign HTTP-запрос
                           │ POST /payment
                           │ Headers: requestId: uuid
                           │ Body: {"amount": 150.50}
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│         Другой микросервис (платёжный сервис)                   │
│  (находится по адресу из ${name.service.url})                   │
│  1. Получает запрос от Feign                                    │
│  2. Генерирует id для платежа                                   │
│  3. Возвращает Payment с id                                     │
└─────────────────────────────────────────────────────────────────┘
```
- OpenFeign — инструмент из проекта Spring Cloud для декларативного вызова HTTP/REST-сервисов.
- Необходимая зависимость — spring-cloud-starter-openfeign из org.springframework.cloud.
- OpenFeign удобно применять для вызова REST-сервисов в Spring-приложениях.
- Для OpenFeign достаточно описать интерфейс — реализацию клиента фреймворк создаст самостоятельно.
- В интерфейсе объявляются методы, которые соответствуют вызовам конечных точек REST.
- Методы снабжаются аннотациями, в которых определяются путь, HTTP-метод и, при необходимости, параметры, заголовки и тело запроса.
- Аннотация над интерфейсом — @FeignClient.
- Минимальная конфигурация @FeignClient обычно включает имя клиента и адрес сервиса:
```java
@FeignClient(
    name = "payments",
    url = "${name.server.url}"
)
public interface PaymentProxy {

    @PostMapping("/payment")
    Payment createPayment(
        @RequestHeader String requestId,
        @RequestBody Payment payment
    );
}

- name в @FeignClient определяет имя клиента, которое используется OpenFeign и Spring для идентификации этого клиента.
- url определяет базовый URL сервиса.
- URI и другие параметры, которые могут зависеть от среды выполнения, лучше хранить в файлах конфигурации, а не жестко прописывать в коде.
- Например, в application.properties: `name.server.url=http://localhost:8080`
- После этого значение можно получить через ${name.server.url}.
- Каждый метод, объявленный в интерфейсе, соответствует вызову конечной точки REST.
- Возможность использовать знакомые Spring MVC-аннотации (@GetMapping, @PostMapping, @RequestBody, @RequestHeader и т. д.) делает OpenFeign удобным в использовании.
- Нужно сообщить Spring, где находятся интерфейсы, определяющие контракты клиентов OpenFeign.
- Для этого используется @EnableFeignClients:
```java
@Configuration
@EnableFeignClients(
    basePackages = "com.example.proxy"
)
public class ProjectConfig {
}
```
- После этого Spring создаст реализации интерфейсов Feign-клиентов, которые можно внедрять в другие компоненты приложения через Dependency Injection.
- Внедрение и использование клиента OpenFeign:
```java
@RestController
public class PaymentsController {
    private final PaymentsProxy paymentsProxy;
    public PaymentsController(PaymentsProxy paymentsProxy) {
        this.paymentsProxy = paymentsProxy;
    }
    @PostMapping("/payment")
    public Payment createPayment(@RequestBody Payment payment) {
        String requestId = UUID.randomUUID().toString();
        return paymentsProxy.createPayment(requestId, payment);
    }  
}
```
- Теперь запустим task6 и task7
- и вызовем конечную точку /payment приложения, используя cURL 
```bash
curl -X POST -H 'content-type:application/json' -d '{"amount":1000}' http://localhost:9090/payment
```

## 11.2 Вызов конечных точек REST с помощью RestTemplate
- `RestTemplate` - инструмент, который применяется для вызова конечных точек REST, начиная со Spring 3 
- `RestTemplate` и сегодня популярен у разработчиков и широкои спользуется в Spring-приложениях
- есть лучшая альтернатива — OpenFeign, поэтому в работе над новыми продуктами, пожалуй, стоит предпочесть именно ее
- Минусы RestTemplate:
    - Нет синхронного и асинхронного вызововов конечных точек;
    - Много шаблонного кода
    - Нет возможности выполнять повторные вызовы и операции отката (логика, которая осуществляется, когда приложение по какой-то причине не может выполнить определенный вызов REST)

- Шаги :
    1) Описать HTTP-заголовки, создав и настроив конфигурацию экземпляра
    `HttpHeaders`
    2) Создать экземпляр `HttpEntity`, в котором представлены данные запроса
    (заголовки и тело)
    3) С помощью метода `exchange()` отправить HTTP-вызов и получить HTTP-ответ

# PS 
## Краткое введение в HTTP
### В.1. ЧТО ТАКОЕ HTTP
- HTTP — это протокол, описывающий то, как клиент веб-приложения обменивается данными с сервером
- Данные передаются в виде текста
- Все HTTP запросы независимы друг от друга

### В.2. HTTP-ЗАПРОСЫ КАК ЯЗЫК ОБЩЕНИЯ МЕЖДУ КЛИЕНТОМ И СЕРВЕРОМ
- HTTP запрос очень простой и состоит из следующих частей:
    - URI запроса           (http://www.manning.com/books/spring-start-here)
    - Метод запроса         (GET, PUT, POST, DELETE и др)
    - Параметры запроса     (10–50символов которые нужно передать серверу)
    - Заголовки запроса     (Данные браузера, и другая информация )
    - Тело запроса          (до нескольких сотен символов, которые клиент передает серверу в рамках запроса)

- URL и URI очень похожи, отличие в том, что у URI есть так же конечый путь (помимо локатора ресурса)
- URI = URL + путь

- Вместе с запросом так же отправляется его метод 
    - GET — отражает намерение клиента получить с сервера какие-то данные; 
    - POST — отражает намерение клиента загрузить данные на сервер;
    - PUT — отражает намерение клиента полностью заменить данные, хранящиеся на сервере (если их нет то создать);
    - DELETE — отражает намерение клиента удалить данные с сервера
    - OPTIONS — вернуть список параметров, поддерживаемых для обработки запросов 
    - PATCH — может использоваться при необходимости изменить лишь часть данных 


- HTTP - запрос может быть направлен через URI, Формуу кнопки на странице, или сценарием, написанным на клиентском языке, например JavaScript
- Параметры запроса представляют собой пары типа «ключ — значение» 
- Клиент добавляет их в HTTP-запрос, чтобы отправить на сервер определенную информацию
- Параметры используют для передачи небольших отдельных элементов данных 
- Если данных больше, лучше их поместить в теле HTTP-запроса



```URI
POST /servlet/default.jsp HTTP/1.1
Accept: text/plain; text/html
Accept-Language: en-gb
Connection: Keep-Alive
Host: localhost
Referer: http://localhost/ch8/SendDetails.html
User-Agent: Mozilla/4.0 (MSIE 4.01;Windows 98)
Content-Length: 33
Content-Type: application/x-www-form-urlencoded
Accept-Encoding: gzip, deflate
Запрос характеризуют метод и путь
Для передачи данных запроса можно lastName=Einstein&firstName=Albert также использовать параметры запроса

```

### В.3. HTTP-ОТВЕТ: СПОСОБ ПОЛУЧИТЬ ОТВЕТ ОТ СЕРВЕРА
- На запрос клиента сервер может от- править следующее
    - Статус ответа (от 100 до 599)
    - Заголовки ответа (необязательные), который содержит небольщой объем данных (10-50 символов) от сервера клиенту
    - Тело ответа (необязательное), модет содержать несколько сотен символов или даже несколько файлов

- Виды статусов ответа (полный список тут https://datatracker.ietf.org/doc/html/rfc7231): 
    - Статусы, начинающиеся с 2, показывают, что сервер понял запрос правильно
    - Статусы, начинающиеся с 4, сервер сообщает клиенту, что с запросом что-то не так и проблема лежит на стороне клиента
    - Статусы, начинающиеся с 5, сервер сообщает о проблеме на своей стороне



### В.4. HTTP-СЕССИЯ
- HTTP-сессия — механизм, позволяющий серверу хранить данные в течение нескольких взаимодействий типа «вопрос — ответ» с одним и тем же клиентом
- Различные запросы и сессии защищены и независимы друг от друга (типа SingleScope)
- Но бывает, что нужно согласовать некоторые запросы между собой (Например Серверу нужен способ узнать, что этот клиент раньше уже добавлял товар в корзину)
- Один из способов реализовать подобное поведение — использовать HTTP- сессию
- Бэкенд присваивает клиенту уникальный идентификатор, называемый «ID сессии», и связывает его с неким местом в памяти приложения
- Каждый запрос, отправляемый клиентом после этого, должен содержать в заголовке ID сессии
- Обычно HTTP-сессия закрывается через какое-то время после того, как клиент перестает отправлять запросы
- Можно обозначить заданное времы вручную (в контейнере сервлетов и в приложении) 


# Резюме
- Веб-сервисы `REST` (Representational State Transfer, передача состояния представления) — это простой способ организовать обмен данными между двумя приложениями
- В Spring-приложениях конечные точки REST создаются на основе механизма Spring MVC
- Необходимо либо использовать аннотацию `@ResponseBody`, чтобы обозначить, что данный метод возвращает непосредственно тело HTTP-ответа
- Либо заменить аннотацию @Controller на `@RestController`, чтобы создать конечную точку REST 
- Если не использовать какую-то изэ тих аннотаций, диспетчер сервлетов будет считать, что данный метод контроллера возвращает имя представления, и попытается найти это представление, вместо того чтобы передать HTTP-ответ
- Можно создать действие контроллера, которое будет возвращать непосредственно тело HTTP-ответа, тогда Spring присвоит этому ответу статус по умолчанию
- Чтобы изменить статус и заголовки HTTP-ответа, действие контроллера должно возвращать экземпляр `ResponseEntity`
- Один из способов обработки исключений — перехватывать их непосредственно на уровне действия контроллера 
- Но иногда такой способ приводит к дублированию кода, чего лучше не допускать
- Вместо того чтобы обрабатывать исключения непосредственно в контроллере, можно вынести логику, которая выполняется в случае, если действие контроллера выдает исключение, в класс совета REST-контроллера
- Конечная точка может получать данные от клиента через HTTP-запрос посредством параметров запроса, переменных пути, а также из тела HTTP-запроса
